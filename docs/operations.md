## Observation and recovery

Cloud metadata and synced files can arrive at different times. The guarantee begins when the poller persists recoverable work. A capture permanently deleted before observation, or a transient collection membership, is not recoverable through current-state polling. The desktop Connector and its file-sync behavior still need user acceptance.

Blob Storage holds immutable snapshots, jobs and analyses, desired-generation pointers, a checkpoint, staging and conflict records. A discovery lease rejects overlap and older observations. Jobs are persisted before checkpoint advancement; queue handoff is reconciled independently. Messages contain only identifiers and have non-expiring TTL. A poison message does not erase its durable job. Unexpected worker failures stop after five recorded attempts. Reconciliation also stops after twenty persisted handoff attempts, including failures before worker startup. Failed jobs require operator replay. Queue delivery has no ordering guarantee.

The importer checks desired generations while holding the discovery lease, verifies generated-file hashes, commits the complete Markdown/JSON/receipt set without force-pushing, then acknowledges cloud jobs. A crash after a push is recovered through the committed receipt. Receipt recovery checks both generated files, including missing files. Lease loss aborts inference and Git commands; every mutable write renews its active leases, uses the ETag observed under that lease, and has a timeout shorter than the lease duration. Git commands run asynchronously so lease renewal continues during a push. The same workflow explicitly builds and deploys because commits made with its default token do not trigger another push workflow. A deployment failure is retried from committed corpus content.

Set `STORAGE_ACCOUNT` and authenticate with Azure CLI for operator commands:

```sh
npm run operate -- status
npm run operate -- replay JOB_ID
npm run operate -- reprocess SOURCE_ID
```

Replay resumes a durable job after infrastructure failure and keeps any cached analysis. Reprocess creates a new generation to retry extraction or replace a failed/outdated analysis. Global `PROCESSING_VERSION` changes force observation and fresh generations. Keep the runtime's configuration and Bicep processing version aligned. Stale generations cannot replace the currently desired generation.

An import conflict appears under `conflicts/{sourceId}.json`. Move intentional edits from generated files into `notes.md`, restore the generated files and receipt from Git, and dispatch the importer again. Do not remove a receipt to bypass the hash check. This describes the historical Git importer. Current SQL ingestion preserves an imported source when it disappears from Zotero.

## Evidence and retention

Source downloads have a 40 MiB per-file limit and a 60-second deadline. Public HTTP(S) downloads check every redirect, pin validated DNS addresses to sockets, and never forward API credentials. HTML scripts and resource loading are disabled. One capture can retain eight attachments totaling 80 MiB, with up to four checked images for analysis. Each image still has a 5 MiB limit, an 8192-pixel side limit and a 40-million-pixel limit. Selection is deterministic across PDFs, text and DOCX, images, and unsupported files. Missing or unreadable siblings produce explicit partial coverage while usable files continue. Scans, locked or malformed files, blocked pages and unsupported formats become explicit review or metadata-only notes. OCR remains disabled. Synced-file absence and transient inference failures have bounded retry before review. Functions has a 20-minute execution timeout. Ingestion gives the model no tools. Chat exposes only the fixed read operations described below.

Raw files are private Blob objects addressed by hash. Active artifacts are retained until deliberate operator deletion. Zotero deletion, trash, and collection removal leave imported app sources active and readable. The app has no source-delete action yet. Its deletion and Zotero cleanup behavior are tracked in [the deletion design issue](https://github.com/DrBushyTop/research-capture-knowledge-base/issues/41). Storage has seven-day soft deletion. No automatic archive purge is configured. Staged validated analysis avoids repeating successful paid inference after repository failures.

Crossref DOI license metadata is recorded as external evidence, not permission to redistribute an arbitrary captured PDF. Note approval and exact-artifact approval are separate fields. Note approval requires both the source fingerprint and the exact approvedGenerationId. Any regeneration, including manual reprocessing, expires old approval. Legacy approval files without a generation fail closed. Missing or stale approval excludes a note from public builds. Public builds serve no raw downloads. Invited readers can open retained PDFs through the owned chat file API.

## Cost and acceptance

Functions has no always-ready instances. The hourly importer avoids five-minute GitHub builds; scheduled imports skip the code verification job, while source pushes run full checks. Private Actions minute allowances, storage operations, inference tokens and consumption execution are metered; observe actual usage before changing frequency. Diagnostic ingestion is capped at 0.1 GB/day with 30-day retention; a reached cap can limit diagnostics. Never log credentials, source text, raw responses or signed download URLs.

Manual acceptance still includes signing into the invited reader account, checking an unintended signed-in account, desktop Connector capture and comfortable reading on the actual Android device. Automation validates cloud captures, generated content, search/filter behavior, private-build restriction and anonymous direct-asset access; it must not claim those human interactions occurred.

## Fuzzy search

The collection uses a prebuilt MiniSearch inverted index in the browser, with prefix matching, typo tolerance and boosted title/topic fields. It makes no model or backend calls. Source type, topic and year filters apply to the fuzzy results. Metadata, generated analysis and human Markdown are always indexed. The private reader and chat index all retained PDF, DOCX, HTML, Markdown, plain text, CSV and JSON text, alongside the bounded analysis input and saved capture commentary. The 180,000-character analysis preview does not cap searchable document text. Scanned PDFs and chart images have no searchable text unless a text layer is present; chat can inspect pages and images when the model needs them.

Azure SQL stores immutable `source-text/{generationId}.json` analysis inputs and `document-text/{generationId}/{artifactHash}/` full-text records before inference. Full-text manifests describe 40,000-character chunks, their hashes, document or page locators, extraction completeness and continuation positions. Chunks are committed before their manifest. Readers reject mismatched source identities, generations, attachment hashes, MIME types or chunk hashes. SQL loads the current generations in batches for search. Historical Blob records and the ignored `.local/search-source-text` cache remain available to export and backfill scripts. The backfill reuses a matching saved input and refuses to reconstruct a multi-attachment capture from only its first file.

Public publishing is deferred. Astro rejects any build mode other than private. Rights metadata and conservative eligibility checks remain dormant for future use. Development indexing runs when `npm run dev` starts; restart after changing corpus files.

## Private dataset chat

The private `/chat/` route submits a question to the Static Web Apps managed API. The proxy checks the invitation-assigned reader role and same-origin POST, then forwards the platform principal with a dedicated function key to the Functions gateway. The gateway checks the role again and binds results to a hash of the signed-in user's provider and ID. The function key stays in server-side SWA application settings. No Azure or model credentials enter the browser or sandbox.

The gateway writes a durable message before queue handoff and returns 202. The React UI polls for completion and tool activity. This keeps requests within the managed API's 45-second limit and avoids paid Static Web Apps hosting. The recovery timer runs independently of Zotero, retries missing handoffs, and stops jobs after two attempts or ten minutes. A reader can run one answer at a time and submit twenty per hour. Messages are capped at 8,000 characters. Stop records cancellation, aborts active model and sandbox work, and leaves the conversation usable. [Managed API limits](https://learn.microsoft.com/en-us/azure/static-web-apps/apis-overview).

Chat is a freeform discussion with the same Sol deployment. Each turn includes recent server-owned conversation history. A conversation started from a document saves its source ID and title as context. Sol can refer to that document and still search the entire corpus. The starting document never restricts its tools. Sol chooses whether to call `search_corpus`, `read_source` or `inspect_media`. Search covers metadata, original extracted text, generated analysis and human Markdown. Empty searches list sources; results can be paginated. Reading can select original documents, analysis, notes or facts. Original text queries find a context window anywhere in retained files. PDF reads can request a page or an ordered range of at most 20 pages, up to page 2000. Tools return bounded passages with the actual returned pages and a continuation offset. DOCX reads use document locators and text offsets because DOCX does not provide stable physical page boundaries. Selecting an attachment keeps citations and file links tied to that file. Inspection sends the actual rendered page or image to Sol and registers a file the answer or citation can display. No source or page selectors appear in the chat composer.

The native agent uses Azure's `/openai/v1/responses` endpoint with medium reasoning and strict JSON output. `store:false` keeps conversation storage in our existing Blob container. Encrypted reasoning items remain in memory between tool rounds. A live check confirmed that this Sol deployment rejects reasoning plus function tools on Chat Completions. Responses supports both. The loop permits eight read operations and two answer-validation corrections, with a 6,000-token output cap per model round. Recent history includes at most twenty turns and 100,000 serialized characters; the complete text context is capped at 300,000 characters. Image bytes and encrypted reasoning are counted by the API rather than that text limit. [Responses migration](https://developers.openai.com/api/docs/guides/migrate-to-responses).

The live chat corpus comes from Azure SQL, independently of frontend deployments. The worker reads current notes, human commentary and source text through its store. Historical Git/Blob chat snapshot scripts have been removed. Retained full-text reads run directly against SQL. Visual inspection and older captures that lack full-text records upload retained artifacts into temporary Azure Container Apps Sandboxes and run the fixed Python driver. Source extraction and rendered assets remain bounded; unsupported file types retain their extraction limitations.

The sandbox group has no managed identity, application credentials or external network access. No arbitrary model-generated code, shell commands, Git writes or package installation run in it. The current regional tooling snapshot is `4daeeb76-0b95-4d8b-9c36-32ea7167fcde`, with Python and PyMuPDF 1.26.7. It was created before any corpus upload. A recreated clean snapshot can be selected with the `sandboxSnapshot` Bicep parameter. Do not snapshot a message workspace. [Snapshot lifecycle](https://sandboxes.azure.com/docs/sandboxes/snapshots).

Each restored sandbox uses 250m CPU, 512 MiB RAM and 5 GiB disk. Functions records the ID before polling, sets a two-minute idle stop and ten-minute automatic deletion policy, and deletes the workspace before calling Sol again. Creation, deletion, file transfers and egress setup use bounded REST requests. This beta SDK drops some request abort signals and treats JSON file downloads as empty binary content, so those operations use bounded REST calls. A recovery sweep also deletes group instances older than ten minutes, including creations whose initial HTTP response was lost. Thus model latency does not hold sandbox compute. The tested SDK is `@azure/containerapps-sandbox` 1.0.0-beta.1 with the preview data API, accepted by the user. Sweden Central currently has one SandboxCore of quota in this subscription. [Sandbox costs](https://sandboxes.azure.com/docs/sandboxes/cost).

Sol returns evidence IDs, optional exact quotes and optional registered attachment IDs. The server rejects unknown citations, unmatched quotes, undeclared inline citations and invented attachments. General discussion can proceed without a corpus citation. Validation checks evidence membership and quoted text, not every interpretation. Citations retain source generation, supporting links and image IDs. PDF downloads use the cited generation even after a source changes. File endpoints check the reader's ownership and the answer's citation or attachment membership before returning bytes; nothing enters the public reader output.

Selected Vercel AI Elements conversation, Markdown message and citation primitives run in an Astro React island. Phone citations open an evidence sheet; desktop citations open on mouse hover or activation with a click, tap or keyboard. Supporting material includes excerpts, notes, sites, PDFs and rendered images. The bottom composer supports multiline phone input, desktop Enter to send, Shift+Enter for a newline, IME input and a Stop control. Phone image viewing uses the full screen, starts at full width, and supports pinch, double-tap, drag panning, keyboard controls and visible zoom buttons. The UI restores conversation history and an active job across reloads. It displays completed answers after validation rather than simulating token streaming.

Readers can paste, drop or attach up to four PNG, JPEG or WebP screenshots per message. The browser scales each to a 2048 px box before upload. The gateway checks the file signature, a 5 MB size limit, an 8192 px side limit and 40 uploads per reader per hour. It stores the bytes under `pipeline/chat/assets/uploads/<owner>/`, so the existing one-day lifecycle rule removes them. Only the uploading reader can attach or view an upload. Sol receives the current message's images as `input_image` data at high detail and up to eight earlier screenshots from the same conversation. Screenshots are never citation evidence.

Deleting a chat checks ownership, writes a tombstone beside the conversation, cancels its pending or running answer and removes saved answers, job files and uploads. A running answer checks the tombstone before saving, so it cannot recreate the chat.

Access requires a Shelf server session for a GitHub login listed in the worker's `READER_GITHUB_USERS` setting, comma separated and currently `pinaatti,DrBushyTop`. Azure verifies GitHub sign-in and the worker checks membership before starting the session. Each private request rechecks the allowlist. Missing configuration denies access.

After the first Functions deployment, configure SWA server settings `CHAT_BACKEND_URL`, `CHAT_BACKEND_KEY` and `READER_ORIGIN`. Generate a function-level key named `swa-proxy` for `chatGateway`; do not use a host master key. Pass the key directly to SWA application settings without printing it or committing it. Bicep provisions the queues, group-scoped worker role, runtime settings and Blob lifecycle rule. Conversations and their saved answers remain until the reader deletes them. Message-job and temporary-file APIs expire after 24 hours from creation. Blob lifecycle removes old jobs, temporary files, cancellation flags and quota records after a day, subject to its asynchronous sweep and the account's seven-day soft-delete retention. It excludes conversations and their deletion tombstones. Earlier uploaded screenshots or rendered pages can therefore expire while the conversation text remains. Sol receives an explicit notice when a replayed screenshot is unavailable. Git notes and archived source artifacts keep their existing retention.

The private reading view uses `GET /api/chat?source=<sourceId>` for saved original text, matched to the current generation and attachment hash. It reads 40,000-character windows and loads later text through `offset`; `attachment` selects a file. Internal full-text reads permit at most 80,000 characters per window, and chat can select PDF page ranges. Saved Zotero notes and annotations remain separate from the document text. Empty text and incomplete extraction stay visible. `GET /api/chat?document=<sourceId>` opens a retained PDF, PNG, JPEG or WebP, or downloads DOCX and supported text files. An optional `attachment` key selects a sibling file. Neither route creates a chat job or makes a model call. Both require an allowed reader and current active corpus membership. The file endpoint checks its 40 MiB limit before downloading, uses an ETag, verifies the hash and format signature, and never serves original HTML.


## Categories and document updates

Only `pinaatti` and `DrBushyTop` have private reader and admin access. `READER_GITHUB_USERS=pinaatti,DrBushyTop` must be present on the Functions worker. Configure it through the Bicep `readerGithubUsers` parameter. Azure invitations and `reader,library_member` role assignments are unnecessary. The public build contains app code only; the backend checks private data access through Shelf's SQL-backed session. See [reader authentication](authentication.md).

`categories/current.json` stores the current registry in the pipeline container. Immutable revisions are under `categories/templates/{categoryId}/{revision}.json`. These settings have no chat retention rule. Conditional writes and the registry lease reject stale edits. Existing notes retain their original headings and template revision; schema-version-1 research notes remain readable.

New capture jobs pin the category registry. The classifier uses the source facts and bounded extracted text, then the analyzer uses the selected template. Manual assignments survive automatic capture updates. Classification alone cannot create source evidence. Metadata-only notes can have a category without invented analysis.

Operator reprocessing also pins the registry, classifies automatically assigned sources, and preserves manual category choices. Existing schema-version-1 notes are not assigned a category by the reader. Use a Categories reclassification batch to migrate them.

Reader notes live under `reader-notes/{sourceId}.json` in the pipeline container, outside chat retention rules. Both invited readers share them. `/api/chat?notes={sourceId}` reads and saves notes after the normal reader authorization checks. Saves take a per-source lease and reject stale revisions with 409. The importer preserves existing commentary and replaces only the marked reader-notes section in `notes.md`. Chat adds current saved notes at answer time; static search picks them up after the importer and rebuild. Reader drafts stay in local browser storage until saved or explicitly discarded.

The Categories page queues read-only previews under the existing processing queue. Preview records use the one-day `chat/assets/category-previews/` retention. Each admin has up to 20 previews per hour. Draft sections remain separate from source text and grant the model no tools.

Saving a template affects future captures. Re-evaluate selected documents to apply it to existing notes, or Check categories to classify automatically assigned documents again. Each durable batch pins its registry and jobs. Dispatch handles five entries per delivery and skips sources superseded by a newer capture or update. Queue reconciliation recovers incomplete handoffs. Processing retries are bounded; failed updates keep existing generated notes and human commentary. Stop pending documents cancels queued work, while a document already running may finish. Retry document resets its recovery budget without discarding successful cached output.

Progress reports Processing until analysis is staged, then Updating reader until the hourly import and deployment publishes that exact generation. Dispatch the GitHub Research pipeline workflow to refresh sooner. The importer retains conflict checks and human files. Search and chat synchronize to the same deployed generations and include generic template sections.

When a page or post has no readable text, the worker can use an available Zotero description or caption. Extraction records `zotero-metadata` and a metadata-only limitation. Search includes that saved text; chat returns it as metadata evidence rather than presenting it as text extracted from the original page. This does not download private social media or infer missing image contents.

## Interactive webpage recovery

HTML extraction first uses the retained original and Readability. Empty HTML, short language/sign-in gates and navigation-only indexes can trigger a separate browser capture when `BROWSER_SANDBOX_SNAPSHOT` is configured. The existing Foundry deployment selects observed browser controls, scrolling, back/reload or finish. It never receives a shell or arbitrary JavaScript tool. Captured content then uses the same category/template analysis path as other source text.

The browser runs in an ephemeral ACA sandbox restored from a clean Playwright image. It receives the source URL and explicit `BROWSER_ASSET_HOSTS`, not corpus data or Azure/model credentials. Document navigation remains same-origin; assets and public read-only API requests may use only those configured hosts. All browser HTTP traffic is intercepted and fulfilled using public-address checks and DNS-pinned sockets, with upstream TLS verification. The browser accepts the sandbox egress proxy's certificate, while the driver independently verifies upstream certificates. Service workers, websockets, uploads, forms, downloads and non-GET requests are blocked. Robots rules are checked for document navigation. Auth/CAPTCHA and consequential controls are not bypassed.

Capture has a six-minute deadline, 40 actions, 20 distinct views, 180,000 characters, at most two content levels beyond the index and a 25 MB network budget. Repeated unproductive actions stop exploration. A partial capture remains explicitly partial. Even an agent-finished capture is a coverage judgement, not proof of complete website coverage. Captures record per-view URLs, times, text and controls, plus action history and screenshot hashes. Screenshots are private blobs. The original artifact remains unchanged; browser capture has a separate cache keyed by source fingerprint and capture version. Reprocessing uses that retained browser evidence rather than silently recrawling on every analysis.

Bootstrap a clean browser image with `scripts/bootstrap-browser-sandbox.ts` under the existing sandbox environment settings, before loading any source content. It installs pinned Playwright and verifies Chromium, then changes egress to deny before creating a snapshot. The current base image is Ubuntu 26.04; Playwright 1.55 uses the Ubuntu 24.04 browser artifact with explicit shared-library installation and a runtime smoke check. Revalidate this setup when upgrading the base image or Playwright. Do not snapshot a customer browsing session. Configure the returned ID as `BROWSER_SANDBOX_SNAPSHOT` and approved dependencies as `BROWSER_ASSET_HOSTS`. For the Ti Delizio menu, observed dependencies are `d35vozid5pezr8.cloudfront.net` and `diegovitaglianosantalucia.tidelizio.app`; these are exact host exceptions, not a wildcard.

The first live test used the language selector, declined optional cookies, selected English and captured dishes, descriptions and prices from Alternative. Coverage was partial; this does not certify the entire restaurant menu. Browser recovery does not turn menu allergen labels into dietary guarantees or infer hidden prices.

## PDF text extraction

The worker uses `@llamaindex/liteparse` 2.15.1 for PDFs with a native text layer. It saves Markdown with headings, paragraph breaks, tables and `<!-- PDF page N -->` markers. The reader renders this format as document text with visible page labels. Older plain-text extractions remain literal text.

OCR is disabled. The parser does not download language models, extract embedded images or render form fields. Scans and sparse documents keep the review or saved-metadata fallback. Full extraction attempts up to 2000 pages and 40 MiB of text, with a hard two-minute deadline in a separate process. It retains page locators, repeated headers and footers, and native text when Markdown reconstruction is empty. Missing text, parser failures and guard limits set full-text completeness to false with a reason. Initial analysis reads only the first 400 pages and at most 180,000 characters. Exceeding that preview sets `extraction.truncated` while later extracted pages remain available to the reader, search and chat.

The production package must include LiteParse's native addon, PDFium library, `dist/pool-worker.js` and our `dist/pdf-document-worker.mjs`. LiteParse's batch path bypasses its own pool, so our parent process enforces the full-text deadline by stopping the child. Both deployment workflows run `node --import tsx scripts/verify-worker-pdf.mjs` after installing production dependencies. This checks actual pooled and isolated batch parsing, plus DOCX conversion and ZIP reading, from the package on Linux before deployment.

Existing source-text records do not change when the parser code changes. Use the existing source reprocessing action for selected PDFs to create new generations and analysis from retained originals. The multiple-attachment, DOCX and full-text change sets the shared and Bicep processing defaults to version `4`. Existing cloud settings can override this default. Align the dev runtime setting after deployment; older generations retain their existing text until reprocessed. The old backfill script fills missing text records, but its immutable `create` call does not replace existing records.

To refresh existing development PDF fixtures without model calls, run `npx tsx scripts/refresh-pdf-text-dev.ts`. It requires `research_dev` and the local blob emulator. An optional directory argument supplies local PDFs when the emulator lacks retained originals. The script matches file hashes, skips missing PDFs and reports counts. It replaces development text and the ignored local cache, not source notes or generated analysis. It refuses a SQL connection-string override. Production must use new generations through reprocessing instead.

## DOCX text extraction

LiteParse supports DOCX through LibreOffice conversion. The worker does not provision LibreOffice, so native DOCX extraction uses Mammoth and validated ZIP input instead. It preserves headings, paragraphs, lists, tables, footnotes, readable headers and footers, and labeled Word comments. Embedded images, charts and objects remain in the retained original with an explicit extraction limitation. Old `.doc` formats remain unsupported.

DOCX input shares the 40 MiB original-file limit. ZIP validation checks paths, duplicate entries, encryption, CRC and actual expanded bytes. Limits are 80 MiB total expanded data, 16 MiB per XML file and 2000 entries. Full text stays separate from the 180,000-character analysis preview. DOCX text has semantic document locators rather than invented page numbers.

## Model prompt cache

Model requests use stable hashed cache keys and canonical schema ordering. Stable instructions precede changing source/view/question data. Chat retains identical tool definitions when its tool budget is reached, using tool_choice=none rather than changing the tool schema. Browser planning appends observations and decisions to a bounded in-memory session; the window resets after eight turns or 100,000 non-image serialized characters. It does not persist model reasoning or browse indefinitely to preserve cache hits.

Exact validated final chat JSON is retained for subsequent turn replay; tool/reasoning transcripts remain transient. This improves final-message prefix reuse, but does not preserve every prefix from earlier tool rounds. Image expiry and bounded history changes can cause expected cache misses. Newer model cache-write charges mean prompt caching is not synonymous with free input.

Use numeric `model-usage` logs for inputTokens, cachedInputTokens, cacheWriteTokens, outputTokens and reasoningTokens to measure actual results. Do not log prompt contents, credentials or plain user identifiers. Missing usage is omitted rather than treated as zero. The exact deployed model was tested with both Responses and Chat Completions cache controls before rollout.
