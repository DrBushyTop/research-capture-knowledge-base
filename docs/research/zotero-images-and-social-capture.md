# Zotero images and social capture

Researched on 2026-10-06. This note distinguishes an uploaded screenshot from a saved social URL and an HTML snapshot. No private library, Instagram account, or representative capture sample was accessed.

## What arrives from Zotero

A screenshot can be added as a normal file attachment. Dragging a file onto an existing item creates a child attachment; dropping it into empty space creates a standalone attachment. Zotero copies files by default. A screenshot attachment contains the saved image bytes, not the source post's structured metadata or other carousel images. The latter distinction follows from the file capture mechanism, not an Instagram-specific guarantee. [Zotero adding files](https://www.zotero.org/support/attaching_files)

A Zotero webpage snapshot is different. The Connector can save a Web Page item with an offline copy of the page, and snapshot saving is configurable. The Connector's SingleFile integration calls `singlefile.getPageData` and returns `pageData.content`. This is saved page content, not a raster screenshot. A downloader must inspect the attachment's actual type rather than treating "snapshot" as an image. [Zotero adding files](https://www.zotero.org/support/attaching_files#web_snapshots), [Connector SingleFile source at revision 876e41ad15139077f2e07b2f71a0fa94742e0b4a](https://github.com/zotero/zotero-connectors/blob/876e41ad15139077f2e07b2f71a0fa94742e0b4a/src/common/singlefile.js)

Stored file attachments live in Zotero's managed data directory and can use file sync. Linked files point to an existing local path, and Zotero does not sync their bytes. A linked URI is another case: it points to a webpage or another program rather than preserving a file copy. A cloud worker cannot infer downloadable bytes from the presence of an attachment record. [Zotero adding files](https://www.zotero.org/support/attaching_files#stored_files_and_linked_files)

Data sync excludes attachment files. File sync handles images and other files separately. Zotero Storage provides web access to attachments and supports group libraries; WebDAV file sync applies only to personal libraries. Therefore item metadata can reach the API before screenshot bytes, and a WebDAV-backed attachment need not be available from Zotero Storage. [Zotero syncing](https://www.zotero.org/support/sync)

The API exposes attachment fields including `linkMode`, `contentType`, `filename`, `md5`, and `mtime`. The documented modes are `imported_file`, `imported_url`, `linked_file`, and `linked_url`. Download a stored file using the attachment item's key at `/users/<userID>/items/<itemKey>/file`. Compare the returned ETag with the attachment's `md5`, then reread metadata on a mismatch. The documentation explicitly warns that newer bytes may exist only in WebDAV. These rules apply to file retrieval; they do not establish screenshot OCR or image enrichment support. [Zotero file API](https://www.zotero.org/support/dev/web_api/v3/file_upload)

## Instagram URL capture

The official translator repository was inspected at revision `3d1c78530f42892328e08741b7cac8474ff687b8`. Its full tree has no `Instagram.js`. A case-insensitive search of the downloaded source archive found only incidental Instagram mentions inside other translators' example metadata, not Instagram URL matching or Instagram media extraction. There is consequently no dedicated Instagram translator behavior to report from that revision. This finding does not exclude private or third-party translators. [Exact repository tree](https://github.com/zotero/translators/tree/3d1c78530f42892328e08741b7cac8474ff687b8), [GitHub tree API](https://api.github.com/repos/zotero/translators/git/trees/3d1c78530f42892328e08741b7cac8474ff687b8?recursive=1)

Zotero documents generic saving when a site is unsupported. The gray webpage icon saves basic page information, and hovering over the Connector icon identifies the translator in use. Embedded Metadata is one default translator, but Zotero cautions that it often finds only minimal metadata. [Unrecognized pages](https://www.zotero.org/support/kb/page_not_recognized), [Default translators](https://www.zotero.org/support/kb/default_translators)

The actual Embedded Metadata attachment logic reads `citation_pdf_url`. It adds a PDF attachment when that value exists; otherwise it adds a document snapshot. This branch does not create a screenshot or download an Instagram carousel or reel. It is generic source behavior, not a tested claim that every Instagram page selects this translator or yields usable content. [Embedded Metadata source, attachment branch](https://github.com/zotero/translators/blob/3d1c78530f42892328e08741b7cac8474ff687b8/Embedded%20Metadata.js#L526-L545)

An Instagram URL alone therefore does not establish preserved images, a complete caption, or downloadable video. Zotero's ability to store and sync video files does not establish automatic reel capture. No Instagram capture test or video extraction guarantee was found in the reviewed primary sources. [Zotero syncing](https://www.zotero.org/support/sync), [Exact translator tree](https://github.com/zotero/translators/tree/3d1c78530f42892328e08741b7cac8474ff687b8)

## Azure OpenAI image input

Azure's vision-enabled Chat Completions API accepts a message `content` array containing text and `image_url` parts. The image value can be a publicly reachable HTTP or HTTPS image URL or a base64 data URL, such as `data:image/png;base64,...`. The deployment must support image input. [Microsoft vision how-to](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/gpt-with-vision)

The documented formats are JPEG, PNG, WEBP, and GIF's first frame. Limits are 10 images per chat request and 20 MB per input image. Lower-detail processing can reduce text-recognition accuracy. Private-endpoint, VNet-restricted, and firewall-restricted image URLs are not supported by the managed image fetcher. Base64 input avoids that external image URL requirement, but still sends the image to the model service. This is an image path, not a documented video-file input path. [Microsoft vision how-to](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/gpt-with-vision), [Microsoft vision concepts and input limits](https://learn.microsoft.com/en-us/azure/foundry-classic/openai/concepts/gpt-with-vision)

## Limits on automatic browser capture

Opening an arbitrary saved URL in a server-side browser introduces SSRF risk. OWASP warns that domain checks alone do not prevent DNS rebinding and that redirects can bypass input validation. Browser subresource requests need controls too, not just the initial navigation. Playwright documents that request routing misses requests intercepted by service workers and recommends blocking service workers when using interception. These sources support a security review of any browser fallback, not a claim that a single URL validator is sufficient. [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), [Playwright browser context routing](https://playwright.dev/docs/api/class-browsercontext#browser-context-route)

Automated social capture also faces site permission and bot controls. Meta describes rate limits and other obstacles against unauthorized automation, and has documented action against unauthorized Instagram scraping. Those publications are historical policy statements, not a legal assessment of this application's proposed capture. No account credentials, anti-bot bypass, or permission to automate Instagram access were established in this research. [Meta scraping controls](https://about.fb.com/news/2021/05/scraping-by-the-numbers/), [Meta Instagram scraping action](https://about.fb.com/news/2020/11/combating-clone-sites/)

The remaining factual check is an authorized representative capture: inspect the resulting parent item, attachment modes, MIME types, synced bytes, and snapshot content. Until then, a screenshot attachment and an Instagram URL must remain separate input cases.

## Implemented scope in this repository

The processing worker accepts one synced PNG, JPEG or WebP attachment, including a standalone image attachment. It retains the original bytes privately in Blob Storage and sends those bytes as a base64 image part to both category classification and template analysis. Reprocessing can restore the retained image without fetching the original again. The image and an optional saved caption stay separate inputs. See `apps/worker/src/extraction.ts`, `image-input.ts` and `enrichment.ts`.

The worker prefers a saved PDF or readable text attachment. When that attachment has no usable text, it tries a synced image attachment on the same parent item. It does not fetch images embedded in HTML or infer a screenshot from an Instagram URL. An image-only source does not get a fabricated source-text record. Its extraction method is `image-vision`, and the reader receives a warning that the output is generated visual interpretation rather than verified transcription. See `apps/worker/src/processing.ts` and `shared/corpus.ts`.

To capture a blocked social page, take a screenshot yourself and attach it to the saved Zotero item using a stored file, then sync the file. Preserve the page URL and any useful caption on the parent item. A screenshot uploaded to chat is currently temporary chat evidence, not a durable Zotero capture or a new source note. See `apps/worker/src/chat-uploads.ts`.

The application limits image inference to one image of at most 5 MiB, 8192 pixels per side and 40 million pixels total. File headers establish MIME type and dimensions before inference. These checks do not guarantee that the model's decoder accepts the file. Invalid or unsupported files remain privately retained and receive a review explanation. Model errors also leave the retained source available for reprocessing.

Automatic browser screenshots are not configured. The worker reports this when page text is unavailable, with a screenshot-attachment fallback. Scanned PDFs without a text layer still need OCR or manual review unless a separate screenshot attachment is available. HEIC, TIFF, SVG, GIF and video analysis are not supported in this processing path. Convert a still image to PNG, JPEG or WebP before capture. Multi-image carousels require separate captures until an explicit multi-image policy exists.
